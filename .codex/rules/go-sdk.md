# Go SDK 通用开发规则

## 适用范围

本规则适用于本仓库的 Go SDK、框架入口及其内部组件。只规定通用工程设计、代码质量和调用体验；具体协议、端点、事件、字段及业务行为以对应的官方文档和项目功能文档为准，不写入本规则。

“必须”表示强制约束；“应”表示默认做法，有充分理由时可以调整；“可”表示按实际需求选择。现有代码不满足某条新规则时，先在相关改动中渐进修正，不为套用规则做无关重构。

## 1. 修改前先确认边界

- 阅读 `go.mod`、README、相关源码、测试和 CI 配置，确认最低 Go 版本、现有用法、公开符号、依赖方向和资源生命周期。
- 先区分调用方可见的契约与内部实现。修改公开符号、默认值、错误类型、并发语义、启动或关闭行为时，评估源码兼容与行为兼容。
- 修复缺陷应有能复现问题的验证；不要删除测试、降低断言或扩大错误容忍范围来掩盖回归。
- 除非任务明确要求，不改模块路径、最低 Go 版本、许可证或发布方式，不顺手引入大型框架和无关重构。
- 标准库与已有依赖优先。新增依赖需有明确收益，并检查维护状态、许可、传递依赖与升级成本。

## 2. 分层、依赖方向与解耦

本仓库当前有 `pkg/goqqrobot` 组合入口、`pkg/config` 配置、`pkg/api` 客户端、`pkg/message` 数据与操作、`shared/types` 共享类型，以及 `internal/adapter`、`internal/core`、`internal/foundation` 等内部实现。新增代码先沿用这些边界；目录只说明现状，不要求为了分层而迁移旧代码。

- 对外入口负责组装和提供简单用法；内部组件负责单一职责。接入适配、核心处理、外部通信、配置装载和基础设施之间保持明确依赖方向，不让内部细节反向控制公共入口。
- 业务无关的核心逻辑不直接读取文件、环境变量、全局单例，也不直接创建不可替换的外部连接；由组合入口传入所需配置与依赖。
- 配置解析与配置使用分离。文件加载可作为便利入口，但核心构造器应能接收内存中的配置，便于嵌入、测试和多实例运行。
- 不让调用方通过 `internal` 导入路径、内部类型或全局状态才能完成正常使用。跨包共享类型只放稳定且确有多个消费者需要的内容；避免把 `shared/types` 变成任意类型的收纳处。
- 包按职责和稳定性划分，名称简短、明确；避免 `util`、`common`、`base` 等无边界的公共包。依赖环应通过调整职责解决，不靠新的万能抽象绕开。
- 协议传输、认证、调度等可变实现与稳定的调用契约隔离。转换只在边界进行，避免外部响应结构或第三方库类型渗入无关层。
- 依赖方向保持可追踪：公开入口组合内部能力，内部核心依赖其所需的最小契约，适配器实现这些契约；不要让核心反向导入公开入口，也不要让两个子包互相调用。
- 只在确有替换需求的边界引入小接口，由消费者定义所需方法；不要为每个结构体配套一个同名公共接口。默认返回具体类型，避免公开接口日后难以扩展。
- 依赖注入以显式构造参数或少量选项为主，不使用服务定位器、隐式注册表或包级可变对象。配置完成后视为只读；不得保留并修改调用方传入的可变对象。

## 3. 面向调用方的公共设计

- 优先让最常见用法有一个清晰入口：构造、注册或调用、启动、关闭。可选能力通过统一风格的配置或选项开放，不要求用户理解内部组装顺序。
- 构造器对明显错误及早返回带字段上下文的错误；只有可能失败时才返回 `(*T, error)`。默认值应安全、有界且可预期，并在文档中说明。
- 少量必需参数直接传入；可选项多时使用配置结构体或选项模式。避免长参数列表、含义不明的布尔参数、同一包多套配置方式。
- 同一概念在各入口的命名、参数顺序、零值含义、错误返回和关闭方式保持一致。命名遵循 Go 惯例，避免重复包名及缩写混乱。
- `context.Context` 用于单次可取消操作，作为第一个参数并命名为 `ctx`；传递到所有相关阻塞步骤。不把单次调用的 context 存在长期对象中。
- 不以 `panic` 表示输入、配置、网络或回调的普通失败。公开方法的同步或异步语义必须清楚；不要暗中开启后台任务或额外操作。
- 所有权明确：调用方注入的资源默认由调用方关闭；SDK 自建资源由 SDK 提供关闭机制。返回的数据、缓冲区与配置对象若会被复用或修改，必须明确复制或借用规则。
- 兼容优先。公开函数签名、接口方法、字段语义、默认行为、错误匹配和生命周期的变化都可能破坏调用方；新增能力优先采用兼容的扩展点。弃用符号保留迁移说明和合理过渡期。
- 为常见路径提供可编译、可复制的短示例，展示构造、取消、错误处理和关闭；高级扩展不应增加基础路径的必填配置。
- 便利入口与可组合入口应共用同一套核心实现，避免两条路径的默认值、错误和生命周期逐渐分叉。便利入口可以装配默认依赖；需要定制的调用方应能替换关键边界，而不必复制整个 SDK 的初始化逻辑。

## 4. Go 代码约定

- 使用 `gofmt`，遵循项目已有命名与文件组织。缩写保持一致；包名不重复出现在导出符号中。接收者名称简短、一致，不在同一类型上无理由混用值接收者和指针接收者。
- 优先清晰的控制流、早返回和标准库类型；不要为了省几行代码引入反射、复杂泛型或深层封装。抽象应减少实际重复与耦合，而非仅减少文本行数。
- 对 nil、空集合和零值定义一致语义；需要区分“未设置”和“显式设置为零”时，使用明确的可选表示。不得依靠隐式零值推断调用方意图。
- 返回的数据若含 map、slice、指针或其他可变成员，应明确是否与内部状态共享；跨边界保留时按需复制，避免调用方修改后影响 SDK 状态。
- 不忽略有意义的错误；确实无需处理时写明原因。不要把失败转换成成功返回，也不要用日志代替错误传播。

## 5. 生命周期、状态和并发

- 为有状态对象定义状态转换：构造后能做什么，何时启动，能否重复启动，关闭是否幂等，关闭后调用返回什么，部分初始化失败如何清理。公开文档与实现保持一致。
- 同一实例是否允许并发调用、注册和关闭必须明确。可并发使用的对象要保护所有共享可变状态；不要持锁执行 I/O、用户回调或可能长时间阻塞的操作。
- 后台 goroutine、队列和缓存必须有停止条件与容量边界。提交任务时明确队列已满、正在关闭和 context 取消的行为；不能静默丢任务或无限阻塞。
- 关闭应停止接收新工作、处理或取消在途工作、释放自建资源；每一步应有可测试的超时或取消边界。不要依赖 finalizer 或进程信号作为唯一清理机制。
- 多实例应彼此隔离。包初始化不应发网络请求、读取凭证、启动 goroutine、打印日志或修改全局默认客户端。
- 回调失败、panic、顺序、并发度和退出策略要明确。除非有明确需要，不在内部异步执行回调；不得让一个回调的异常无意破坏整个进程。

## 6. 错误、诊断与安全

- 错误应说明操作与原因，并保留根因；包装时使用 `%w`。需要调用方分支处理的稳定错误提供 `errors.Is` 或 `errors.As` 可用的形式，不要求解析错误文本。
- 对取消、截止时间、关闭状态、输入错误与外部失败作清晰区分。返回非 nil 结果和非 nil 错误时，文档必须说明结果能否使用。
- 库默认返回错误给调用方决定如何记录；不要在各层重复打日志，也不要直接写全局 logger 或标准输出。可选诊断入口应默认无操作，并与调用方的日志框架解耦。
- 错误、日志、格式化输出和示例不得暴露凭证、密钥或敏感载荷；对可能含敏感信息的结构体不要直接使用 `%+v`。必要的脱敏在边界统一处理。
- 外部输入在进入核心逻辑前完成必要且稳定的校验；不要用过严的本地校验阻止未来仍然合法的数据。对读取、缓存、队列、重试与等待设置合理上限。

## 7. 注释与文档

- 每个公共包应有以 `Package 包名` 开头的包注释，说明用途、主要入口和最重要的并发或生命周期约束。
- 每个导出类型、函数、方法、常量组和有非显然语义的导出字段应有 GoDoc 注释，以标识符开头。注释写调用契约和限制，不复述名称或逐行翻译代码。
- 对外注释按需说明：参数有效范围、nil 与零值、默认值、错误与结果并存语义、取消、并发安全、资源所有权、调用顺序、关闭后行为及兼容性约束。
- 内部注释解释难以从代码看出的“为什么”：不变量、同步策略、边界条件、权衡和外部约束。简单赋值、显而易见的流程不加噪声注释。
- 项目代码中的英文说明注释必须保留原文，并在每一行英文的紧接下一行添加对应中文翻译；适用于包注释、GoDoc、内部注释、行尾注释、测试和示例。已有纯中文说明无需补英文；翻译须保持原意和术语一致，代码标识符保持 Go 惯例。多行英文逐行对应翻译，不能只在段末补一段中文。
- 编译或工具指令（例如 `//go:build`、`//go:generate`、`//line`、`//export`、`//nolint` 和 cgo 前导声明）不是普通说明注释，不得因翻译改变指令语义、必需位置或紧邻关系；字符串中的 URL、协议文本及测试载荷也不得作为注释处理。
- 注释及中译须随行为修改同步更新，不能保留失效的 TODO、注释掉的大块旧实现或与当前签名不符的示例。
- `TODO` 应写具体待办及触发条件或关联问题；`Deprecated:` 应指出替代入口和迁移方向。必要时用简短示例说明容易误用的契约。
- README 和示例应能通过仓库外部调用方的视角使用，不能依赖 `internal` 包；功能变更同步更新相关文档与迁移说明。

注释示例（名称仅示意，重点是说明契约）：

```go
// Shutdown stops accepting new work and waits for accepted work to finish.
// Shutdown 停止接收新工作，并等待已接受的任务结束。
// Cancellation returns ctx.Err(); repeated calls are safe.
// ctx 取消后返回 ctx.Err()；重复调用是安全的。
func (s *Service) Shutdown(ctx context.Context) error
```

## 8. 设计模式的使用边界

模式只用于解决真实变化点，不以套用术语为目的。优先选择能用少量代码表达、方便调用方理解的形式。

| 场景 | 合适模式 | 使用条件与边界 |
| --- | --- | --- |
| 组装多个内部组件 | 构造器与组合根 | 集中校验、注入依赖和清理失败的部分初始化；避免组件自行查找全局依赖。 |
| 替换外部依赖或测试替身 | 小接口与适配器 | 接口放在消费侧，只包含实际需要的方法；一个实现且没有替换需求时用具体类型。 |
| 多种可替换处理策略 | 策略模式 | 行为确实随配置或场景变化时注入策略；默认策略明确，避免为单个分支建立层层接口。 |
| 简化常见用法 | 门面模式 | 对外暴露少量稳定入口，内部职责仍分离；门面不承担全部实现。 |
| 多个处理步骤或回调 | 处理链或中间件 | 需要组合、顺序和短路时使用；约定错误传播、取消和执行顺序。 |
| 创建时的可选配置 | 配置对象或函数选项 | 可选项确实较多时选其一，设置冲突、默认值和校验时机明确。 |
| 资源释放与关闭 | 显式生命周期 | 用 `Close`、`Shutdown(ctx)` 等契约表达；避免隐藏后台清理或全局钩子。 |

不要预先引入抽象工厂、通用事件总线、反射注册容器或层层包装。新增模式前，先说明它隔离了哪个变化点、减少了哪些调用方负担，以及失败和关闭语义如何传递。

## 9. 测试与交付

- 使用标准 `testing` 包和项目已有工具。测试关注公开行为与边界，不按实现逐行镜像；缺陷修复应覆盖原故障及关键失败路径。
- 测试优先注入依赖或使用本地替身，避免真实外部服务、真实凭证、固定端口和时间敏感的长时间 `Sleep`。并发和关闭逻辑要覆盖取消、重复关闭、在途工作及竞态。
- 示例应能编译，并展示推荐的调用方式。测试夹具不包含真实密钥；集成测试与常规单元测试隔离。
- 修改 Go 代码后按范围运行 `gofmt`、`go test ./...`、`go vet ./...`；涉及并发时运行 `go test -race ./...`。若项目有额外 CI 检查则遵循现有约定。只有实际执行过的检查才能写为通过。
- 文档修改后检查标题、链接、术语、示例和规则之间是否矛盾。最终说明改了什么、为何这样设计、实际验证结果及仍存在的限制。
